# 1. 우리가 답해야 하는 질문

관제사에게 이 한 문장에 답해야 합니다.

> **지금 울산항 어느 부두에, 어떤 액체화물(위험물 포함)이, 얼마나 있는가.
> 그리고 그 배치가 혼재금지·흘수·기상 기준을 위반하는가.**

이 질문을 데이터로 쪼개면 네 가지가 필요합니다.

| 알아야 하는 것 | 필요한 데이터 | 어디서 |
|---|---|---|
| 어느 배가 액체화물선인가 | 선종(ship kind) | PORT-MIS 입출항신고 |
| 그 배가 지금 어디 있는가 | 실시간 위치 | UPA 항내 선박위치 API |
| 무슨 화물을 싣고 있는가 | 화물 manifest, UN번호 | UPA 통합화물정보 *(업체코드 대기 → 합성으로 선행)* |
| 그 화물이 얼마나 위험한가 | MSDS, IMDG 등급 | KOSHA MSDS API + IMDG Code |

---

# 2. AIS를 먼저 이해해야 합니다 — 신호가 두 종류입니다

이걸 모르면 뒤의 모든 이야기가 이해되지 않습니다.

**AIS는 하나의 신호가 아니라 두 종류를 따로 쏩니다.**

| | **동적신호** | **정적신호** |
|---|---|---|
| 메시지 | Message 1/2/3 (Class A)<br>Message 18 (Class B) | **Message 5** (Class A)<br>**Message 24** (Class B) |
| 담긴 내용 | MMSI, 위경도, 속력, 침로 | **호출부호, IMO번호, 선명, 선종, 흘수, 목적지** |
| 주기 | 2초 ~ 3분 (속력에 따라) | **6분 고정, 그것도 쏘는 배만** |

즉,

- **위치는 계속 옵니다** → MMSI 결측률 **0%**
- **선종·호출부호는 가끔, 배에 따라 아예 안 옵니다** → 호출부호 결측률 **31%**

우리가 쓰는 UPA `getVslPstnInfo` API는 UPA가 이 둘을 합쳐 한 줄로 내려주는 것입니다. 그 순간 정적신호를 못 받았으면 호출부호 칸이 비어서 옵니다.

# 3. ★ 배 크기에 따라 문제가 3계층으로 갈립니다

**여기가 이 문서에서 가장 중요한 부분입니다.** 지금까지 이 셋을 뭉뚱그려 이야기해서 혼란이 있었습니다.

| 계층 | 어떤 배 | AIS로 오는 것 | 우리 화면에 | 문제 |
|---|---|---|---|---|
| **①** | 대형 상선<br>(유조선·케미칼선·LPG선) | 동적 + 정적 **전부** | ✅ 뜸 | **없음** |
| **②** | 중소형·관공선<br>(소방정·경비정·순찰선·예선) | 동적만 (정적 미송출) | ✅ **뜸** | **식별**이 안 됨 |
| **③** | **부선(barge)·초소형선** | **아무것도 안 옴** | ❌ **안 뜸** | **존재 자체를 모름** |

## ②와 ③은 완전히 다른 문제입니다

- **② = 식별(identification) 문제** — 배는 화면에 있는데 "무슨 배인지"를 모릅니다.
- **③ = 탐지(detection) 문제** — 배가 화면에 **아예 없습니다.**

**우리가 지난주 고친 150척은 ②입니다.** ③이 아닙니다. 이 구분이 중요합니다.

## ★ 흔한 오해 정정 — "IMO 번호가 없어서 AIS에 안 나온다"

**아닙니다. 둘은 별개의 제도입니다.**

| | IMO 번호 | AIS |
|---|---|---|
| 무엇 | 선박 **등록번호** (7자리) | 무선 **송신 장비** |
| 근거 | SOLAS 제XI-1장 제3규칙 | SOLAS 제V장 제19규칙 |
| 대상 | 여객선 100GT 이상<br>화물선 300GT 이상 | 국제항해 300GT 이상<br>비국제항해 500GT 이상<br>여객선 |
| 특징 | 평생 불변 (선적·선명 바뀌어도 유지) | 안 달면 아무 신호도 안 옴 |

**"IMO 번호가 없다"는 식별 키 하나가 없다는 뜻이고, "AIS가 없다"는 배가 레이더에서 사라진다는 뜻입니다.** 둘 다 작은 배에서 일어나지만 원인도 결과도 다릅니다.

> 다만 하나는 사실입니다 — **IMO 번호는 호출부호와 같은 정적신호(Message 5)에 실려 옵니다.** 그래서 "호출부호가 없는 관측은 IMO도 없다"는 맞습니다. 실제 데이터로 확인했습니다:
>
> ```
> callsgn  = LARB8       ← 정적신호(Msg 5)
> imoNo    = 9877428     ← 정적신호(Msg 5)   ★ 호출부호와 같은 메시지
> mmsiNo   = 224998000   ← 동적신호(Msg 1/2/3)  ★ 항상 옴
> lat/lot/sog/cog        ← 동적신호
> ```
>
> **이래서 "IMO를 기본키로 쓰자"는 제안을 채택하지 않았습니다.** IMO를 키로 삼으면 호출부호와 똑같이 31% 이상 비고, 정작 문제인 부선·소형선은 IMO 자체가 없어 행조차 만들 수 없습니다.

# 4. ③번(부선·소형선)을 어떻게 식별하나 — AIS를 포기하고 다른 소스를 씁니다

**결론부터: AIS로는 안 됩니다. 신호를 안 쏘는 배를 신호로 찾을 수는 없습니다.**
대신 **AIS와 완전히 독립적인 소스 5개**가 있고, 우리는 이미 그중 상당수를 갖고 있습니다.

## 4-1. PORT-MIS 입출항신고 ← 가장 확실한 방법

**작은 배도 입출항신고는 합니다.** 신고는 AIS와 무관한 행정 절차입니다.

실제 우리 데이터(451건)에서 확인했습니다:

| 선종코드 | 선종 | 건수 |
|---|---|---|
| **93** | **급유선(벙커링선)** | **19척** |
| 61 | 견인용예선 | 14척 |
| 69 | 기타 예선 | 5척 |
| 79 | 기타 부선 | 1척 |

**AIS가 못 잡는 급유선 19척이 PORT-MIS에는 잡혀 있습니다.** 이게 답입니다.

그리고 이 판정용 플래그를 이미 만들어 뒀습니다:

```python
is_liquid_cargo_vessel   # 액체화물 본선 (선종 51~59)
is_liquid_cargo_barge    # 액체화물 부선 (선종 73 원유·74 석유제품·75 화공약품 운반용)
is_bunkering_vessel      # 급유선 (선종 93)
```

## 4-2. 예선(tug) 항적으로 부선을 간접 추적

부선은 **비자항**입니다. 스스로 못 움직이고 예선이 끌거나 밉니다.

- **부선은 AIS가 없지만, 끄는 예선은 있습니다.**
- 예선이 액체부두 쪽으로 움직임 + PORT-MIS에 부선 입출항신고 존재 → 시간·위치로 연결

우리 데이터에 견인용예선 14척 + 기타예선 5척이 있으니 추적 대상이 확보돼 있습니다.

## 4-3. 벙커링전용정박지 위치 ← 이미 코드표에 있음

`ulsan_facility_codes.py`에 이미 들어 있습니다.

```
WAB-11, WAB-12, WAB-21, WAB-22, WAB-31, WAB-32  = 벙커링전용정박지 B11~B32
```

**여기 있는 배는 벙커링(급유) 중입니다.** 선종을 몰라도 위치만으로 용도가 확정됩니다.

## 4-4. UPA 화물 manifest (B/L 단위)

화물은 선박이 아니라 **B/L(선하증권) 단위**로 신고됩니다. 부선에 실린 화물도 B/L로 잡힙니다.
*(현재 업체코드 `bzentyCd` 발급 대기 중 → 확보 시 즉시 연결 가능)*

## 4-5. 계선시설코드 ← 가장 강한 근거

**배가 어느 부두에 붙었는지만 알면 취급화물이 확정됩니다.** 선종도 호출부호도 필요 없습니다.

```
MDU-03~08  SK 3~8부두     → 유류
MDS-01~03  S-OIL 1~3부두  → 유류
MDG-01~02  정일 1~2부두   → 액체화학
MBL-01     가스부두        → 가스(LPG/LNG)
...  총 43개 액체 시설
```

추정이 아니라 **항만 공식 시설 지정**이라 근거로서 가장 강합니다.

## 정리 — 계층별 처방

| 계층 | 해결 방법 | 상태 |
|---|---|---|
| ① 대형 상선 | AIS + PORT-MIS | ✅ 됨 |
| ② 중소형·관공선 | MMSI-First로 화면에 유지 + `UNIDENTIFIED` 표시 | ✅ 됨 |
| ③ **부선·초소형** | **PORT-MIS 신고 + 예선 추적 + 정박지 + 계선시설** | 🔜 플래그는 있음, 연결 남음 |

# 5. 지난주에 고친 것 (②번 계층)

## 5-1. 무슨 일이 있었나

`mart` 뷰가 **호출부호를 선박 고유키로** 쓰고 있었습니다.

```sql
WHERE callsgn IS NOT NULL   -- ← 호출부호 없으면 통째로 버림
```

그 결과 **항내 522척 중 150척이 마트에서 사라졌습니다.** 지도에도 안 뜨고 안전판정 대상에서도 빠졌습니다.

## 5-2. 처음 세운 가설과 그 결과

> "정적신호가 6분 주기니까 어떤 스냅샷에선 빠질 수 있다. 그럼 그 MMSI의 **가장 최근 호출부호를 끌어와 채우면(Stateful Filling)** 되지 않나?"

논리는 맞았고 SQL도 정확했습니다. 그런데 **실측하니 회복되는 배가 0척이었습니다.**

```
고유 MMSI 516척
  항상 호출부호 있음   : 366척
  일부 스냅샷만 있음   :   0척  ← 채우기가 회복하는 대상
  한 번도 없음        : 150척  ← 끌어올 과거가 없음
```

**"일부만 있음"이 0척**이라는 게 결정적입니다. 결측이 랜덤이 아니라 **특정 선박군에 100% 몰려 있다**는 뜻이니까요. 즉 **간헐적 누락이 아니라 체계적 미송출**입니다.

## 5-3. 그래서 처방을 바꿨습니다

**고유키를 호출부호(결측 31%) → MMSI(결측 0%)로 교체하고 필터를 제거했습니다.**

**결과: 위치보유 선박 372척 → 522척 (150척 복구, 유실 0)**

채우기 로직은 폐기하지 않고 보조로 남겼습니다. 수집 주기를 올리면 곧바로 효과가 생기는 코드고, 부수적으로 버그도 하나 고쳤습니다 — 예전 뷰는 결측 선박의 최종위치시각을 **한 시간 전 값**으로 표시했는데 지금은 실제 최신 시각이 나옵니다.

## 5-4. ★ 여기서 한 번 판단을 틀렸고, 교차검증에서 잡혔습니다

처음에는 이렇게 썼습니다.

> "결측 150척은 소방정·경비정·예선이니 액체화물선 식별에 손실이 없다."

**이 판단은 철회했습니다.** 근거로 든 것은 *이번 표본에서 관찰된 사실*인데 *구조적 보장*처럼 서술했습니다. 3장에서 본 것처럼 울산·온산에는 소형 액체 운반체가 상시 움직입니다.

**그래서 판정을 2값에서 3상태로 바꿨습니다.**

| `identity_confidence` | 의미 | 실측 |
|---|---|---|
| `CONFIRMED` | PORT-MIS 신고로 선종 확정 | 360척 |
| `PARTIAL` | 신고는 없으나 정적신호로 식별됨 | 15척 |
| **`UNIDENTIFIED`** | 정적신호 이력 없음 → **"안전"이 아니라 "미확인 위험"** | 150척 |

**핵심은 모르는 것을 안전 쪽이 아니라 위험 쪽에 둔다는 것입니다.**

> **@함현우** — `UNIDENTIFIED` 선박은 **회색으로 흐리게 하지 마세요.** 흐리면 "덜 중요한 배"로 읽힙니다. 주의 색 + 물음표로 표시하고, 클릭 시 "VTS 교신으로 확인 필요"를 띄워주세요.

# 6. 울산항 실무 관점에서 빠져 있던 것 (4건 중 3건 수정)

교차검증과 별개로 "이 데이터로 실제 액체부두를 운영할 수 있나"를 기준으로 재점검했습니다.

## 6-1. ✅ 흘수 판정에 조위가 빠져 있었습니다 — 가장 큰 실무 오류

기존 판정식은 `선박 흘수 < 부두 수심`이었습니다. **실무는 다릅니다.**

**(1) 부두 명세의 수심은 해도기준면(Chart Datum) 기준입니다.** 해도기준면은 약최저저조위라, 실제 가용수심은 항상 그보다 큽니다.

```
가용수심 = 해도수심 + 그 시각 조위
```

조위를 빼먹으면 **"만조에만 접안 가능한 배"를 영구 접안불가로 오판합니다.** 실제로 대형 유조선은 이 조위 여유에 맞춰 접안 시각(tidal window)을 잡습니다. 스케줄링 시스템이 이걸 모르면 존재하는 선택지를 스스로 지웁니다.

**(2) 흘수 = 수심이면 되는 게 아닙니다.** 선체 아래에 **UKC(용골하 여유수심)** 가 남아야 합니다. 항주파·선체 침하·해저 기복·측심 오차를 흡수하는 여유입니다.

**→ `mart.berth_draught_check` 뷰를 만들어 조위를 실제로 결합했습니다.**

| 부두 | 해도수심 | 조위 | 가용수심 | 흘수 | UKC | 요구 | 판정 |
|---|---|---|---|---|---|---|---|
| SK8 | 18.0 | 0.38 | 18.38 | 11.0 | 7.38 | 1.10 | `OK` |
| SK3 | 12.0 | 0.38 | 12.38 | 11.9 | 0.48 | 1.19 | `MARGINAL` |
| SK1 | 7.5 | 0.38 | 7.88 | 11.0 | −3.12 | 1.10 | `NOT_ALLOWED` |

**`MARGINAL`이 핵심입니다** — "지금은 안 되지만 만조엔 된다"를 표현할 수 있어야 스케줄링이 성립합니다.

> **한계 2건 (보고서에도 명시)**
> ① UKC 10%는 **관행값이지 법정 수치가 아닙니다.** 터미널 운영규정으로 확정해야 합니다.
> ② AIS 흘수(`drft`)는 **선원이 손으로 입력하는 값**이고 트림(선수·선미 흘수 차)을 반영하지 않습니다. 실제 최대흘수는 이보다 클 수 있으니 보수적으로 보세요.

## 6-2. ✅ 부두 이름이 소스마다 달라 조인이 전면 실패하고 있었습니다

"계선시설코드로 화물을 확정한다"는 계획이 진척되지 않던 **실제 원인**입니다.

| 소스 | 표기 |
|---|---|
| UPA 운항관제 | `울산본항 제4부두` |
| PORT-MIS CODE BOOK | `4부두` (코드 `MB4-01`) |
| 우리 데이터 | `SK1부두`, `정일1부두` |

**데이터가 없어서가 아니라 이름이 안 맞아서 막혀 있었습니다.** `upa_port_call`에 `facility_spec_code='U04'`, `facility_name='울산본항 제4부두'`가 이미 들어와 있었습니다.

**→ 정규화 함수를 추가해 세 표기를 맞췄습니다.**

```
"울산본항 제4부두"             → "4부두"       → 액체화학 → 액체부두 ✅
"SK 3부두" / "SK3부두"         → "SK3부두"     → 유류     → 액체부두 ✅
"S-Oil 1부두"                  → "S-OIL1부두"  → 유류     → 액체부두 ✅
"정일스톨트헤븐울산신항 3부두" → "정일3부두"   → 액체화학 → 액체부두 ✅
"화암부두"                     → "화암부두"    → (미표기) → None(판정불가)
```

부수로 **가스부두 오분류**도 고쳤습니다. 취급화물이 "가스"라 액체 키워드에 안 걸려 비액체로 분류되고 있었는데, LPG·LNG는 액화가스이고 우리 하역 대상입니다. → 액체 시설코드 **42 → 43개**

> 여기도 같은 원칙입니다 — 판정 함수가 True/False뿐 아니라 **`None`(판정 불가)** 을 반환합니다. 모르는 걸 False(비액체=안전)로 뭉개면 위험물이 화면에서 사라집니다.

## 6-3. ✅ 기상 판정이 풍속만 보고 있었습니다

세 값 모두 **이미 수집돼 있었는데 마트에서 안 꺼내 쓰고 있었습니다.**

| 값 | 왜 필요한가 |
|---|---|
| **풍향** | **이안풍(offshore)** 이면 계류삭 장력이 급증합니다. 같은 풍속도 방향에 따라 위험도가 다릅니다 |
| **돌풍(gust)** | 계류삭은 평균풍속이 아니라 **순간최대풍속**에 끊어집니다 |
| **조류** | 액체부두 접·이안 조종의 직접 제약. 울산 본항·온산 수로는 창·낙조류 방향이 접안에 영향 |

시정(visibility)은 이미 있었지만, **울산항은 해무가 잦아 시정이 실질적 병목**이라 위반 시나리오에 시정 조건(1,200 m — 도선 제한)을 명시했습니다.

## 6-4. ⚠️ 하역 소요시간이 없어 "스케줄링"이 성립하지 않습니다 (미해결)

지금 시스템은 **"누가 어디 있고 안전한가"** 는 답하지만 **"다음 배를 언제 붙일 수 있나"** 는 답하지 못합니다.

필요한데 없는 것:
- **하역 소요시간** — 물량 ÷ 펌프 레이트(터미널별 상이). 펌프 레이트 데이터 없음
- **선석 점유 종료 예정(ETD)** — 현재 `departure_at_utc`는 실적이지 예정이 아님
- **도선사·예선 가용성** — 실제 병목은 선석이 아니라 도선사인 경우가 많음
- **선석 제원** — 수심만으로 배정 불가. **선박 길이(LOA) > 선석 길이**면 접안 못 함

이 중 **선석 제원은 UPA 선석시설 API로 확보 가능**하니 우선 착수 대상입니다.

# 7. 혼재금지 판정을 "위법"에서 "확인필요"로 바꿨습니다

## 7-1. 무엇이 문제였나 (쉽게)

우리는 **IMDG Code 7.2 "일반격리표"** 를 써서 혼재금지를 판정하고 있었습니다. 이 표는 이런 식입니다.

```
Class 2.1(인화성가스) ↔ Class 3(인화성액체)  = 2   → "Separated from" (다른 격창에 둬라)
Class 2.1(인화성가스) ↔ Class 8(부식성)      = 1   → "Away from" (수평 3m 이상 띄워라)
Class 8(부식성)       ↔ Class 3(인화성액체)  = X   → 일반 규정 없음
```

**그런데 이 표는 "배 안에서 화물을 어떻게 떨어뜨려 실을 것인가"를 정한 규정입니다.**
화물창(hold)과 갑판(deck) 이야기지, **부두 A와 부두 B 사이 거리 이야기가 아닙니다.**

국내 법령 계보도 똑같습니다.

```
「선박안전법」 제41조
  → 「위험물 선박운송 및 저장규칙」(해수부령) 제20조 (위험물의 격리)
    → 「위험물 선박운송 기준」(해수부 고시) 별표19
```

**이 계보 전체가 '선박에 실은 위험물'을 대상으로 합니다.**

## 7-2. 심사에서 나올 질문

> "IMDG 7.2는 배 안에서 화물 떨어뜨려 놓으라는 규정인데, 왜 그걸 부두 A와 부두 B 사이 거리에 적용했죠?"

**이 질문에는 답이 없습니다.** 실제로 그 규정이 아니니까요.

## 7-3. 그래서 어떻게 했나 — 말로 방어하지 않고 데이터에 사실대로 적었습니다

교차검증은 *"보수적 기준을 차용했다고 방어 논리를 세워라"* 라고 조언했지만, **말로 방어하면 심사에서 또 물립니다.** 대신 **시스템이 애초에 "위법"이라고 주장하지 않게** 바꿨습니다.

**바꾼 것 3가지:**

**① `rule_authority` 컬럼 신설** — 각 판정 규칙이 어떤 권위에 근거하는지 표시

| 값 | 의미 | 해당 시나리오 |
|---|---|---|
| `법정근거` | 국내 법령·고시에 직접 근거 | UN번호 누락, 포장기준 위반 |
| **`차용-스크리닝`** | **해상 규정을 항만 상황에 보수적으로 차용** | **혼재금지 3건** |
| `운영기준` | 터미널·항만 운영 실무 기준 | 흘수(UKC), 기상 임계 |

**② 근거 서술에 단서 명기**

```
"IMDG 7.2 일반격리표 Class 2.1↔3 = 코드 2 — Separated from(다른 격창)
 / ※ 선내 적재 규정을 인접 선석 스크리닝에 차용(법정 위반판정 아님)"
```

**③ 판정 문구 자체를 바꿈**

| | 문구 |
|---|---|
| ❌ 이전 | "**혼재금지 경고** — Separated from 요구, **인접 선석 동시 취급 불가**" |
| ✅ 현재 | "**확인필요 경고** — **한 선박에 함께 실렸다면** Separated from 대상. 인접 선석 동시하역 가부는 **터미널 운영규정으로 확인**" |

**차이가 보이시나요?**
- 이전은 "**이건 위법이다**" 라고 단정합니다 → 근거를 대라고 하면 못 댑니다
- 현재는 "**이 조합은 배에 함께 실으면 격리 대상인데, 지금 옆 선석에서 동시에 다루고 있으니 확인하세요**" 라고 말합니다 → **전부 사실이라 반박당할 지점이 없습니다**

## 7-4. "표가 대칭이고 2.1↔8 = 1로 확정" 이 무슨 말인가

김동안 님이 만든 `imdg_segregation_loader.py`에 **IMDG 7.2 일반격리표 원문**이 17×17 행렬로 들어 있습니다. 저는 그걸 정본으로 삼아 두 가지를 프로그램으로 확인했습니다.

**(1) 대칭성 검사** — 표가 제대로 입력됐는지 보는 무결성 검사입니다.

격리 규정은 **"A와 B를 떨어뜨려라"** 이므로, A행-B열 값과 B행-A열 값이 **반드시 같아야** 합니다. 다르면 표를 옮겨 적을 때 실수한 것입니다.

```
17×17 = 289칸 전부 대조 → 모두 일치 (대칭성 검사 통과)
```

**(2) 우리가 쓰는 3개 조합의 값 확정**

교차검증(Antigravity)이 `2.1 ↔ 8 = "1 (Away from) **or 2**"` 라고 애매하게 답했는데, 정본 표를 직접 조회하니 **`1`로 확정**이었습니다. "or 2"는 근거가 없습니다.

| 조합 | 정본 값 | 의미 |
|---|---|---|
| Class 2.1 ↔ 3 | **2** | Separated from (다른 격창) |
| Class 2.1 ↔ 8 | **1** | Away from (수평 3 m 이상) ← "or 2" 아님 |
| Class 2.3 ↔ 3 | **2** | Separated from (다른 격창) |

**참고 — 저도 전에 여기서 틀렸습니다.** 처음에는 `8↔3`(부식성↔인화성액체)과 `2.3↔2.1`(독성가스↔인화성가스)을 혼재금지로 넣었는데, 정본 표와 대조하니 **둘 다 `X`(일반 규정 없음)** 였습니다. 실무 직관에 기댄 추정이었고 근거가 없어 전량 폐기했습니다.

# 8. 합성 화물 데이터의 화학적 정합성 (WBS 1.5 / 2.4)

## 8-1. 왜 합성 데이터를 쓰나

UPA 통합화물 API는 **업체코드(`bzentyCd`)** 발급이 외부 절차에 묶여 있습니다. 확보 시점을 우리가 통제할 수 없는데, 화물이 없으면 마트·백엔드·안전판정 에이전트가 전부 대기 상태가 됩니다.

**그래서 스키마 정의서와 컬럼명·순서·타입이 완전히 일치하는 39컬럼 합성 데이터를 만들었습니다.** 실데이터가 오면 생성기만 끄면 됩니다.

## 8-2. 합성 데이터가 정당하려면 갖춰야 할 4조건

합성 데이터 자체는 아무것도 입증하지 못합니다. 아래를 **데이터 컬럼 수준에서 강제**해야 정당합니다.

| 조건 | 어떻게 강제했나 |
|---|---|
| 실데이터와 절대 안 섞임 | 전 행 `is_synthetic=True`, `source_system='UPA_SYNTHETIC'` |
| 스키마가 실데이터와 동일 | 39컬럼 순서까지 일치 |
| 생성 근거가 실데이터에서 유도 | 화물은 **PORT-MIS 실선종**에서, 부두는 **실재 액체부두**에서 |
| 언제 폐기되는지 명시 | `cargo_basis` 컬럼에 행별 생성 근거 기록 |

## 8-3. ★ 여기서 실제 오류 3건이 나왔습니다

교차검증이 *"UN번호 ↔ 정식선적명 ↔ IMDG Class 삼각관계가 어긋나면 신뢰도가 추락한다"* 고 지적했고, **대조해보니 정말 틀려 있었습니다.**

| # | 틀린 내용 | 정정 | 왜 문제인가 |
|---|---|---|---|
| 1 | 원유운반선 화물 = **UN1993** (FLAMMABLE LIQUID, N.O.S. — 총칭) | **UN1267** (PETROLEUM CRUDE OIL) | 총칭 UN을 쓰면 MSDS가 엉뚱한 물질로 매칭됨 |
| 2 | LNG운반선 화물 = **UN1971** (METHANE, **COMPRESSED**) | **UN1972** (METHANE, **REFRIGERATED LIQUID**) | LNG는 압축가스가 아니라 냉동액화 |
| 3 | 메탄올 UN1230의 **부차위험 6.1(독성) 누락** | 참조표에 수록 | Class 3(인화성)만 보면 **독성 노출을 놓침** |

**세 건 모두 "39컬럼 스키마 정합"으로는 절대 안 잡힙니다.**
**스키마 정합과 내용 정합은 별개**라는 게 이 정정의 교훈입니다.

## 8-4. 구조적 조치 — 사람이 손으로 못 적게 만들었습니다

`data_pipeline/reference/imdg_dgl.py` 를 만들어 **화물명·UN·Class·부차위험·용기등급의 유일한 출처**로 삼았습니다.

- 생성기는 값을 직접 적지 않고 **전부 이 표에서 유도**
- **`enforce_dgl()` 이 CSV를 쓰기 전에 전 행을 검증**하고, 불일치가 하나라도 있으면 **생성 자체를 중단**
- 선종별 허용 UN 목록으로 **해운 실무상 넌센스 조합도 차단** (LPG선에 황산 같은 것)

## 8-5. 근거 수준을 숨기지 않았습니다

IMDG Code 원문을 직접 못 봤으므로, **각 항목에 근거 수준을 플래그로 남겼습니다.**

| `verified` | 의미 | 현재 |
|---|---|---|
| `UNMR` | UN Model Regulations 계열 공개 DB와 대조 확인 | **6종** |
| `MSDS` | KOSHA MSDS 원문(N02/N06/N08)과 기계 대조 확인 | 0종 |
| `TODO` | **아직 어떤 1차 출처와도 대조 안 됨** | **16종** |

대조 확인된 6종:

```
UN1267  PETROLEUM CRUDE OIL            Class 3         PG I/II/III
UN1971  METHANE, COMPRESSED            Class 2.1
UN1972  METHANE, REFRIGERATED LIQUID   Class 2.1        ← LNG
UN1005  AMMONIA, ANHYDROUS             Class 2.3 (8)
UN1093  ACRYLONITRILE, STABILIZED      Class 3 (6.1)   PG I
UN1230  METHANOL                       Class 3 (6.1)   PG II
```

> **주의할 점:** ADR(육상)과 IMDG(해상)는 **UN Model Regulations를 공통 모체**로 하므로 UN번호·정식선적명·등급·부차위험·용기등급은 두 규정에서 일치합니다. 하지만 **격리(segregation)·적재(stowage)·EmS는 IMDG 고유**라 이 대조로 검증되지 않습니다. 혼재금지 근거는 계속 7.2 일반격리표(7-4장)를 씁니다.

**남은 16종은 IMDG Code Vol.2 Chapter 3.2 원문 대조가 필요합니다.** 보고서·시연에 인용하기 전에 확보해야 합니다.

### 이 자료가 채운 공백 4가지

**① 하역 소요시간 — 6-4의 "스케줄링이 성립하지 않는다"에 첫 실측 근거**

현대오일터미널이 유일하게 시간당 처리량을 명시합니다(하역 2,400 kl/h).

```
소요시간(h) ≈ 물량(kl) ÷ 레이트(kl/h)

20,000 kl → 8.33 h
50,000 kl → 20.83 h
100,000 kl → 41.67 h
```

> 레이트가 확보되지 않은 9개 터미널은 `None`을 반환합니다. **0이나 평균값으로 대체하지 않습니다** — 모르는 걸 아는 척하면 스케줄이 실제보다 낙관적으로 나옵니다.
> 또한 이건 **순수 이송 시간**입니다. 접·이안, 호스 연결, 검량, 서류 시간은 빠져 있어 실제 선석 점유시간은 더 깁니다.

**② 선석 흘수 제한 — 6-1의 `berth_draught_check` 확장 근거**

Vopak이 `Draught 11.0 meter / Berths for vessels: 3`을 명시합니다. 정일 최대 DWT 10만톤, 오드펠 50,000 DWT도 있습니다. 기존에는 SK 부두 수심 8개뿐이었습니다.

**③ 터미널별 실제 취급화물 — 합성 데이터의 부두 배정 근거 격상**

기존 계선시설 코드표는 `액체화학` / `유류` 같은 **대분류**뿐이었는데, 브로슈어는 **물질명 수준**입니다. Methanol·Xylene·Benzene·Styrene Monomer·Propylene Oxide 등은 우리 DGL 참조표의 UN 번호와 직접 연결됩니다.

```
태영인더스트리   → 1,2-에폭시프로판(1280), 스티렌(2055), 크실렌(1307), 벤젠(1114)
한국보팍터미날   → 메탄올(1230), 크실렌(1307), 스티렌(2055)
온산탱크터미널   → 가솔린(1203), 경유(1202), 케로신(1223)
```

> 브로슈어에 있으나 DGL 미등재인 물질(MEG·MPG·MEA·MEK·A.N·HMD·Diisocyanate·에틸렌)은 **의도적으로 비워 뒀습니다.** 지어내지 않습니다.

**④ ★ 3장 ③계층(부선·소형 급유선)의 활동 구역 특정**

지금까지 "부선·소형 급유선이 AIS에 안 잡힌다"는 건 알았지만 **어디서 움직이는지**는 몰랐습니다. 브로슈어가 그걸 좁혀줍니다.

| 설비 | 터미널 | 의미 |
|---|---|---|
| **벙커링 설비** | 유나이티드터미널코리아, 울산에너지터미널, 온산탱크터미널 | **소형 급유선의 주 활동 구역** |
| **STS(선박간 이고작업)** | 유나이티드터미널코리아 | **부선·소형선 접현이 실제로 발생하는 지점** |
| **Barge 접근 명시** | 한국보팍터미날 (`Access: Barge / Pipeline / Truck / Vessel`) | **부선이 직접 붙는 터미널** |

**정일·UTK·오드펠·온산 4곳이 블렌딩 설비/허가를 갖고 있습니다.** (오드펠은 국내 최초 허가)

블렌딩은 **화물 특성 자체를 바꿉니다** — 인화점·옥탄가·증기압이 달라집니다. 즉 **UN 번호를 고정값으로 보면 안 되는 경우가 울산항에 실제로 존재합니다.** 안전판정에서 유의해야 할 지점입니다.

## 12-2. ISGOTT 관련 논문 — MSDS 사용의 국제적 정당성 확보

**"Ensuring Safety and Compliance: MSDS Implementation in On-Board Blending of Pertalite (RON90)"** (Ilham Ashari, Alifia Rachma / Politeknik Ilmu Pelayaran Semarang, 2023)

인도네시아 해양대 논문이라 우리 항만과 직접 관계는 없지만, **인용된 국제 규정 두 개가 우리 약점을 메웁니다.**

### ① IMO Resolution MSC.150(77) (2003)

> "Recommendation for Material Safety Data Sheets (MSDS) for **MARPOL Annex I Cargoes and Marine Fuel Oils**"

**IMO가 유조선 화물과 선박연료유에 대해 MSDS 제공을 명시적으로 권고한 결의입니다.**

지금까지 "MSDS는 산업안전(KOSHA) 문서인데 해상 위험물 판정에 써도 되나?"라는 질문에 국내 규칙(제18조)밖에 댈 게 없었습니다. 이제 **국제 규정 근거**가 생겼습니다.

→ V-DG-01(위험물 UN번호 누락) 시나리오의 `rule_basis`에 반영했습니다.

### ② ISGOTT 6th Edition (OCIMF/ICS, 2020) p.10

> MSDS는 **GHS 형식**을 따르며 **16개 섹션**으로 구성된다.

우리가 KOSHA MSDS를 `msdsItemCode` 기준 **16섹션**으로 파싱하는 방식이 ISGOTT가 규정한 구조와 동일하다는 확인입니다.

> **다만 선을 그어야 합니다** — 두 근거 모두 "MSDS를 참조하라"는 것이지 **"MSDS가 IMDG 분류를 대체한다"는 뜻이 아닙니다.** UN번호·Class·용기등급의 정본은 여전히 IMDG Code 3.2입니다.

### ③ 부수 확인 — ISGOTT 6th ed. ch.12.1.6 (블렌딩)

논문의 주제가 **선상 블렌딩 시 MSDS 미준수로 발생한 위험**입니다. SOLAS 제VI장 제5-2규칙이 물리적 블렌딩을 정의합니다. 12-1에서 확인했듯 **울산항 4개 터미널이 실제로 블렌딩을 합니다.**
